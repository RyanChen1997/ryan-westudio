# 文字一致性：仅首次 AI 结构化阶段

## 校验对象与时机

```text
用户原文
   ↓ 程序提取/冻结，先于 AI 修改
source.md + source-manifest.json
   ↓ AI 只另写结构稿
structured.md
   ↓ 对照原文文字，失败返回 AI 修正
Tiptap 所见即所得编辑器
   ↓ 用户/AI 在同一会话中进行被接受的编辑
直接复制当前版本
```

唯一的内容对照是 `source.md → structured.md`。不是结构稿与它自己比，也不是只比较结构稿与 HTML。编辑器打开后不对用户修改重跑原文检查；界面没有校验按钮、后台校验任务或单独发布预览。

## 程序入口

```bash
# 1. AI 整理前冻结。Word 输入换成 --docx。
npm start -- --project <目录> --md <用户原文.md> --prepare-only

# 2. AI 读取 source.md，另写 structured.md，不修改 source.md。

# 3. 自动对照，通过后才启动编辑器。
npm start -- --project <目录> --md <目录>/structured.md --source-md <目录>/source.md --open
```

- `source.md` 与清单使用只读权限保存；清单记录 SHA-256。后续原文误改，即使结构稿也跟着改了，哈希检查仍会阻止启动。
- 哈希只用于保护基准；不能拿两份 Markdown 的文件哈希直接证明文字一致，因为添加 `#`、`**` 等必然改变文件字节。
- 独立 `--source-md` 也可以指向可信的原始 Markdown；若没有冻结清单，就不能声称有“AI 整理前已捕获”的哈希证据。Skill 正式流程必须先 prepare。
- 未传原文基准的直接导入仍可使用编辑器，但 CLI 明确提示未进行 AI 结构化前后对照，不显示假通过。
- 只读文件和哈希用于防误改，不是抵抗拥有同账户权限、同时篡改原文和清单的恶意行为的密码学证明。

## 对照规则

实现：`modules/editor/core/source-validation.mjs`，与正文导入共享 Markdown 词法解析器。

1. 按原顺序提取标题、正文、列表、引用等的文字。忽略 Markdown 格式标记，不忽略标题文字。
2. 归一排版空白；保留标点、数字、英文大小写和词间分隔。已有代码内容及代码空白单独逐字检查。
3. 图注、替代文字、正文链接地址及其对应文字范围同样不能在结构化时悄悄更改。链接按归一正文中的位置绑定，不能只保留相同 URL 列表却把链接挪到另一个词（包括相同词的另一次出现）。初始报告 policyVersion 为 2；旧项目的历史报告不重跑或冒充升级。该检查不做图片 OCR，也不是图片文件存在性检查。
4. 对照失败给出首个差异附近的原文/结构稿片段，不采用“相似度足够高就算通过”。
5. 初始报告含原文与结构稿哈希、标题处理方式、差异和结果，保存在 `project.json.sourceValidation`；此报告属于初始阶段，不随用户编辑重新认证或覆盖。

### 标题怎么处理

| 变化 | 结果 |
|---|---|
| `## 原标题` 改成 `# 原标题` | 字没变，允许 |
| 给原句包 `**` 或转成引用 | 字没变，允许 |
| 原文开头完整标题移到 frontmatter，正文不再重复 | 比较时将该标题计回，允许 |
| 原文已有 frontmatter 标题被换成另一标题 | 不允许假称与原文一致 |
| 原来没有文章元信息标题，AI 新拟 frontmatter 标题 | 单独记录为新元信息，不当作原正文文字 |
| 将原小标题概括改写，或新增概括性小标题 | 是文字变化，检查不豁免，不能通过删除所有标题来掩盖 |
| 删除、重排正文，修改数字、标点或大小写 | 不通过 |

当前采用保守规则。若新增/改写标题确有必要，需单独得到授权并明确内容变化；不能给比较器设置“忽略全部标题”的漏洞。用户授权整体改写时，先完成独立内容编辑并确认，再以确认稿作为排版输入，保留旧稿，不谎称完全保留原文。

## 用户进入编辑器后

用户改字、标题、图注或图片，以及通过 AI tools 发出的被接受操作，更新当前 Tiptap 状态和语义 Markdown；不再与初始 source.md 比较。初始报告不会阻挡这些修改。

复制/导出直接从当前版本生成正文，进行必要的图片编码和版本一致性处理，不运行文字检查，也不切换到另一份发布内容。Schema、保存 CAS、资源读取等仍有正常错误处理，但不是面向用户的校验步骤。

编辑视图和输出必须共享模板样式、行内标记嵌套、列表布局和装饰图。差异由开发测试发现、修复，而不是让用户点击一个预览开关规避。`tests/export-contract.mjs` 只是开发回归断言，不在编辑器或复制链路中运行。

## 范围与限制

- Word 先由程序提取为基准 Markdown，原 Word 另行备份；本检查证明 AI 未改动已提取的内容，不证明 Word 解析器对文本框、嵌入对象、图片文字等完全无遗漏。解析警告必须明确处理，不能静默宣称完整。
- 排版空白被归一，不承诺原始 Markdown 字节相同。正文顺序、标点、数值等不使用模糊匹配。
- 结构稿的 `title` 仍按原规则对照；`publish-title` 是单独的发布拟题，`digest` 是简介，均不参加正文文字对照。打开编辑器后发布拟题成为可编辑的文章标题，当前 Markdown 将标题与简介保存在 `title` 和 `digest`。正文和原标题在冻结原文中保留。发布拟题和简介都不是完成排版的必填项。
- 本地所见即所得与实际微信粘贴是两个边界。微信可能再过滤样式或拒绝内联图片，仍需人工检查；不通过自动上传用户资料绕过平台限制。
